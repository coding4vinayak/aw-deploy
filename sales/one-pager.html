LeadWorks

$49/mo · flat

Lead intake that refuses duplicates at the door and hands the desk a clean CSV.

They say: “our lead lists are a mess — dupes, junk fields, exports that break.”

Prove it: demo/run-demo.sh leadworks — a duplicate refused 409 at the door, validation trail, dedupe sweep, signed lead.created / export.completed deliveries, CSV export, the buyer’s own CSV imported with the bad row named on its line, an enrichment rule that visits exactly the leads it names (2 of 24), the button on one lead’s row that visits that one lead (1 of 19, processed=1, one visit stamp added across the whole workspace), and the visit that then fills the gap: a Managing Director becomes C_LEVEL while the seniority a person typed survives, an ambiguous title gains nothing, and every lead’s 0–100 is computed from its own row — four prospects walk in and are priced 20 / 90 / 96 / 49 with the terms they earned stored beside the number, a typed 82 kept as an override next to the 96 the row earns, and what a rule declares in actions is honoured, not decorative: the rule that asks for seniority fills it (C_LEVEL, a SUCCESS [seniority] log) and the one that asks for industry fills nothing it was not asked for (the visit is still stamped, the log says PARTIAL with nothing in it), a declaration this build cannot perform is refused 400 at the door with the offending part named, and a SCHEDULED rule stating a cron the sweep can read queues its own job inside the minute — first job after 39 s, where the same rule used to queue none at any hour; and the log now says what the row said, not only what it became — the visit the row refused stores beforeData {"seniority":"VP"}, the answer the rule never asked for stores nothing, and the two records that used to be byte-identical are split; the gap that was filled stores null beside C_LEVEL; and when two rules want the same column in the same minute the number the operator set says which one writes it — three rules created 50, 90, 10 come back from the list door as 90, 50, 10, and the sweep minute that follows queues two jobs for three due rules: the top-ranked carries seniority, the weakest is left with only companySize, and the middle one queues no job, logs no row, records no creditsUsed. Move the bottom rule’s number to 95 and the next minute hands it both columns and starves the one that owned them a minute earlier. A finished export now carries the date its own download door closes: Export.expiresAt was in the schema from the first migration, every export door handed it back, and nothing filled it or read it — measured on the running app, 25 completed exports and 0 expiries, the oldest four days old and still serving 200, with the word “expired” living only in the error for a file the operating system had already reclaimed. The worker stamps the lifetime in the one update that finishes a file, and both download doors ask that date before they open it: 200 with all 957 bytes while the row says so, then 410 — export retired on the date the row itself names, the same words from both doors, the row still COMPLETED with the same filePath. And the minute after that date the file itself is gone: planPurge asks the row's own date first, then the shape the worker can actually produce, and the application's only unlink acts on what it returns, on the once-a-minute sweep — the 957 bytes above were reclaimed 34 s into the next step while the row still read COMPLETED with the same filePath, both doors kept answering the retired sentence rather than the lost-file one, and the 24 files no row names stayed exactly where they were: a lifetime nobody promised is not a licence to delete.
